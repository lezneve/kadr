# kadr / технічний аналіз і архітектура

робоча назва: **kadr** (від «кадр»). тимчасова, у коді живе в одній константі `APP_NAME`.

статус: етапи 1–4 прийнято; етап 5 — release candidate 0.1.0-rc.1. перевірка з живим вводом і на кількох моніторах ще попереду — testing.md. цифри — у [measurements.md](measurements.md), що перевірено і що ні — у [testing.md](testing.md).

---

## 0. продуктовий контракт

**що це:** windows-утиліта, яка швидко робить скриншот і кладе його в буфер обміну та/або у файл.

**платформа:** windows 10 1703+ (з цієї версії є per-monitor-v2 dpi) / windows 11, x64.

**основні сценарії:**
1. гаряча клавіша → виділення області → копія в буфер + png у папці.
2. гаряча клавіша → активне вікно.
3. гаряча клавіша → монітор під курсором.
4. трей: зробити скриншот, налаштування, вихід.

**не робимо (без окремого погодження):** все з розділу 5 брифу — відео, gif, ocr, хмари, редактор, плагіни, аналітика, автооновлення.

**бюджети:** baseline виміряно (measurements.md), числові бюджети ще не встановлено — це рішення команди, а не агента.

---

## 1. rust + tauri v2 + vanilla ts: доцільність

ключове спостереження: **kadr — резидентна програма.** майже весь час вона лежить у треї. тому головна вартість — пам'ять і процеси в стані очікування, а не розмір інсталятора.

у застосунку три різні частини, і їх оцінюємо окремо:

| частина | як часто живе | вимоги |
|---|---|---|
| резидентне ядро (трей, гарячі клавіші) | завжди | мінімум ram, нуль cpu |
| overlay вибору області | кілька секунд на скриншот | з'являється за десятки мс, повнорозмірний кадр |
| вікно налаштувань | рідко | гарний, доступний інтерфейс |

**overlay у webview — погана ідея незалежно від решти:**
- холодний старт webview2 — це запуск кількох процесів chromium, а overlay має з'являтися одразу;
- overlay показує «заморожений» кадр; передати 2560×1600×4 = 16 мб (або 100+ мб на кількох 4k) через ipc у webview — саме те, що бриф забороняє (§7.2);
- тримати прихований webview заради швидкості порушує §4.2 (overlay не живе у фоні).

тому **overlay — нативне win32-вікно з gdi**. кадр уже лежить у dib section, overlay просто блітить його.

**захоплення, буфер обміну, збереження, гарячі клавіші, трей** — це win32 api, які rust викликає напряму через crate `windows`. tauri тут нічого не додає: його трей і global-shortcut — обгортки над тими ж `Shell_NotifyIcon` і `RegisterHotKey`.

отже tauri залишається кандидатом **лише для вікна налаштувань**.

## 2. порівняння з нативними альтернативами

```text
user journey:   hotkey -> overlay -> select -> clipboard + png. settings відкривають рідко.
constraints:    резидентний процес, ram/cpu у простої важливіші за розмір інсталятора.
candidate a:    tauri v2 (tao/wry + webview2) для налаштувань, нативне win32-ядро всередині.
candidate b:    чистий rust + win32, налаштування — нативний діалог.
candidate c:    rust + win32 ядро, налаштування — webview2 напряму (webview2-com).
measured:       measurements.md, розділ «spike: tauri vs native у треї».
```

**що показали вимірювання:**
- **у простої — нічия.** у треї без вікон tauri майже не дорожчий за чистий win32: private 1.9 vs 1.4 мб, cpu 0 в обох. вартість простою рішення **не визначає**.
- відкрите webview-вікно tauri коштує ~145 мб private у 7 процесах. для c не вимірювали; там той самий webview2, тож очікуємо близьке значення — це припущення.
- після закриття вікна процеси webview2 завершуються (перевірено); хост лишає +3.5 мб private.
- tauri коштує в іншому: exe 3.0 мб проти 0.1–0.2 мб, 208 crate-ів проти 15, чиста збірка 157 с проти 18–22 с. за пріоритетами брифу (§14) це нижче за правильність і зручність.
- **перевірено:** власне win32-вікно з `wndproc` у головному потоці отримує повідомлення, коли цикл крутить tao. ядро, побудоване навколо прихованого вікна, переживе перехід на tauri.

**рішення (погоджено командою):**
1. **ядро (трей, гарячі клавіші, захоплення, overlay, буфер, збереження) — чистий rust + win32.** реалізовано на етапі 3.
2. **вікно налаштувань — нативне (b), у власному короткоживучому процесі.** порівняно на етапі 4 з тією самою сторінкою в tauri (measurements.md): вигляд і доступність рівні, а tauri коштує ~210 мб private у 7 процесах проти ~11.5 мб в 1 процесі, поки вікно відкрите. tauri не підключено.
   - стандартні контроли windows (кнопки, радіокнопки, прапорець, поле) дають клавіатуру й ролі для екранного диктора; comctl6 custom draw + direct2d/directwrite дають вигляд з макета. темна тема — власне малювання; заголовок — документовані `DWMWA_USE_IMMERSIVE_DARK_MODE`, `DWMWA_CAPTION_COLOR` і `DWMWA_TEXT_COLOR` (windows 11; windows 10 їх ігнорує), без недокументованих викликів;
   - окремий процес, бо direct2d/directwrite після першого використання лишають у процесі 5–8 мб, яких резидентний kadr не повинен нести (виміряно). процес говорить з kadr через `settings.ini` і два повідомлення вікну kadr;
   - c (webview2 напряму) відкинуто ще на етапі 1.

**revisit when:** налаштування стануть складнішими за одну сторінку, або ціна webview2-вікна виявиться помітною на слабких машинах.

інші варіанти, які розглянуто й відкинуто:
- **winui 3 / wpf / winforms (.net або c++/winrt):** .net-рантайм або windows app sdk — важчий старт і пам'ять для резидентного процесу; c++ — гірша безпека пам'яті, ніж rust.
- **egui / iced / slint:** власний рендер, свій event loop, gpu-контекст у резидентному процесі; «не нативний» вигляд і слабка доступність (screen reader) в egui. для однієї сторінки налаштувань — зайве.
- **electron:** окремий chromium у кожній збірці — суперечить усій філософії.

## 3. захоплення екрана у windows

| api | плюси | мінуси | для kadr |
|---|---|---|---|
| **gdi `BitBlt` з desktop dc** | є всюди, синхронний, один виклик для всього віртуального екрана, від'ємні координати працюють без окремої логіки, нуль залежностей | на hdr-дисплеях, за звітами, неправильні кольори; drm-вміст чорний (і це правильно) | **mvp** |
| **dxgi desktop duplication** | швидкий, gpu, для потокового захоплення | окремо на кожен вихід, d3d11-ініціалізація, складніші повороти й hdr; для одного кадру — overkill | ні |
| **windows.graphics.capture (wgc)** | сучасний, вікна й монітори, hdr, перекриті вікна | winrt + d3d11, асинхронний перший кадр, win10 1803+; жовту рамку можна вимкнути лише з 20348 і лише після згоди користувача (`RequestAccessAsync(Borderless)` + capability у маніфесті пакета) | кандидат на потім (hdr) |
| **`PrintWindow(PW_RENDERFULLCONTENT)`** | вікно, навіть перекрите | деякі застосунки (ігри, gpu-вікна) повертають чорне | fallback для вікна, якщо знадобиться |

**рішення:** `BitBlt` + `CAPTUREBLT` (щоб потрапляли layered/напівпрозорі вікна).

- **область:** заморожуємо весь віртуальний екран одним `BitBlt` → overlay показує цей кадр → вирізаємо прямокутник із захопленого кадру. те, що бачив користувач, і є результатом; overlay на знімок фізично не потрапляє.
- **активне вікно:** `GetForegroundWindow` + `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` (без невидимих рамок win10/11), обрізане межами екрана → `BitBlt`. якщо активне — робочий стіл, панель задач або згорнуте вікно, знімаємо монітор під курсором. вікна, що перекривають активне, потрапляють на знімок (це `BitBlt` з екрана, а не з вікна).
- **монітор:** `MonitorFromPoint(курсор)` → `GetMonitorInfo` → `BitBlt`.
- **dpi:** per-monitor-v2 оголошено в маніфесті (`kadr.manifest`, вбудовується лінкером у `build.rs`), тож усі координати й `BitBlt` — у фізичних пікселях ще до першого рядка коду. перевірено: 2560×1600 при 150 %.

**відоме обмеження:** hdr — **не перевірено** (на тестовій машині hdr немає). вирішуємо через wgc тільки якщо це стане реальною проблемою.

## 4. залежності

| потреба | рішення | альтернатива, яку відкинуто |
|---|---|---|
| усі win32/com виклики | `windows` 0.62 (microsoft), features увімкнено точково | `winapi` — не підтримується; власні ffi-декларації — більше ручного `unsafe` |
| png | **wic** (входить у windows) | `png` crate (+`miniz_oxide`, `crc32fast`, `fdeflate`…) — зайве, якщо ос уже вміє |
| час для імені файла | `GetLocalTime` | `chrono` |
| системні папки | `SHGetKnownFolderPath` | `dirs` |
| налаштування | текстовий `key = value`, ~150 рядків з тестами | `serde` + `serde_json` — для восьми значень це фреймворк заради формату; власний парсер дає точні повідомлення з номером рядка |
| маніфест (dpi, стиль діалогів) | `/MANIFESTINPUT` лінкера msvc у `build.rs` | `embed-resource` / `winres` |
| іконка трею | малюється в коді під розмір і тему панелі задач | `.ico`-ресурс (потрібен компілятор ресурсів) |

**одна** пряма залежність (`windows`). транзитивно — 10 crate-ів з того ж репозиторію microsoft/windows-rs і 4 стандартні proc-macro (`syn`, `quote`, `proc-macro2`, `unicode-ident`), які працюють тільки під час компіляції.

## 6. життєвий цикл і процеси

```text
старт ──> маніфест: per-monitor-v2 dpi, common controls 6
     ──> один екземпляр (mutex Local\kadr.instance), com для wic
     ──> settings.ini, якщо є (інакше — значення за замовчуванням)
     ──> приховане звичайне вікно (не message-only: тільки звичайні вікна
         отримують TaskbarCreated після перезапуску explorer)
     ──> Shell_NotifyIcon + RegisterHotKey, проблеми — одним діалогом
     ──> MsgWaitForMultipleObjectsEx: спить, поки немає повідомлень або
         зміни файла налаштувань. жодних періодичних таймерів, потоків, опитування

hotkey ──> область: BitBlt віртуального екрана -> затемнена копія -> overlay
           (власний модальний цикл, як у діалогу) -> mouse up / esc / права кнопка
       ──> вікно / монітор: одразу BitBlt прямокутника
       ──> crop -> clipboard (CF_DIB) -> png -> файл
       ──> overlay знищено, усі кадри й gdi-об'єкти звільнено -> знову сон

з трею  ──> захоплення через одноразовий таймер 250 мс, щоб меню встигло зникнути
налаштування ──> kadr запускає `kadr --settings-window` і чекає на цей процес
                 у тому самому MsgWaitForMultipleObjectsEx
             ──> кожна зміна: settings.ini атомарно -> повідомлення kadr ->
                 перечитати, перереєструвати клавіші
             ──> запис комбінації: kadr звільняє клавіші, вікно перевіряє, чи
                 комбінація вільна (RegisterHotKey), потім kadr реєструє знову
             ──> закриття: процес завершується, вся його пам'ять повертається;
                 якщо він впав посеред запису, kadr повертає клавіші сам
             ──> файл можна правити й руками: зміна файла -> таймер 300 мс ->
                 перечитати
вихід ──> UnregisterHotKey, NIM_DELETE, кінець циклу (також при завершенні сеансу)
```

резидентно — один процес, один потік (вікно налаштувань — окремий процес, тільки поки відкрите). кодування png (~52 мс для 2560×1600) іде синхронно після того, як overlay уже зник, тому користувач його не бачить. окремий потік додамо, тільки якщо вимірювання покажуть, що це заважає.

файл налаштувань з'являється тільки після першої зміни в налаштуваннях.

## 7. ризики для пам'яті й продуктивності

1. **повнорозмірні кадри.** 2560×1600×4 = 16 мб; три 4k-монітори ≈ 100 мб. overlay тримає два буфери (оригінал + затемнена копія), тож пік ≈ 2× віртуального екрана. виміряно на 2560×1600: пік private 33.6 мб, після закриття — 2.2 мб. останній знімок не кешується.
2. **wic.** після першого кодування dll wic лишаються завантаженими: working set після знімка 12–28 мб (система підрізає його з часом), private — 2.6 мб проти 1.6 мб до першого знімка. далі не росте (20 знімків поспіль, testing.md).
3. **перемальовування overlay.** на кожен рух миші перемальовується прямокутник, що охоплює старе й нове виділення (з рамкою й підписом), через буфер поза екраном. вартість росте з площею: < 1 мп — ~1 мс, 1–3 мп — ~5 мс, ≥ 3 мп (майже весь екран 2560×1600) — ~11 мс. на 4k і кількох моніторах велике виділення коштуватиме пропорційно більше — **не виміряно**. якщо це стане помітним, перемальовувати тільки смуги, що змінились (різниця старого й нового прямокутника), а не весь прямокутник.
4. **вікно налаштувань**: ~11 мб private в окремому процесі, поки відкрите; резидентний kadr лишається на 1.7–2.3 мб (виміряно). webview2 не використовується.
5. **hdr / захищений вміст** — коректність, не продуктивність.
6. **PrintScreen.** у windows 11, починаючи з build 22621.1928, голий PrtSc за замовчуванням забирає snipping tool. **перевірено на цій машині:** `RegisterHotKey(VK_SNAPSHOT)` повертає успіх, але `WM_HOTKEY` не приходить. тому:
   - з гілки `feature/editor` за замовчуванням: область `printscreen`, вікно `alt+printscreen`, екран `ctrl+shift+printscreen` (settings.ini з рядком `hotkey_region` зберігає свою клавішу; вікно налаштувань завжди записує всі рядки);
   - якщо голий `printscreen` призначено, а системне перехоплення увімкнене (явне значення в реєстрі, або build 22621.1928+ без нього), kadr **один раз питає** при старті, чи вимкнути його (`src/snipping.rs`). тільки після «так» записує `HKCU\Control Panel\Keyboard\PrintScreenKeyForSnippingEnabled = 0` і зберігає попереднє значення в `HKCU\Software\kadr`; видалення kadr повертає як було. «ні» поважається; повторний запис printscreen у налаштуваннях питає знову. snipping tool не видаляється й не змінюється;
   - чи діє зміна без виходу з сеансу — **не перевірено** (потребує реального натискання PrtSc), тому діалог прямо каже «якщо не діє — вийдіть і увійдіть»; пункт у manual-checklist;
   - **виміряно на цій машині, з увімкненим перехопленням windows:** голий `VK_SNAPSHOT` без модифікаторів вдалося зареєструвати двом процесам одночасно (`RegisterHotKey` у другому процесі теж успішний; з `alt` — `ERROR_HOTKEY_ALREADY_REGISTERED`). тобто конфлікт з іншою програмою знімків на голому PrtSc kadr може не побачити — це сказано в README. чи так само з вимкненим перехопленням — **не перевірено** (`tests/printscreen-probe.ps1`, manual-checklist 2.11); тести перевіряють реєстрацію за трасою, а не пробою;
   - тести працюють з підставним ключем `HKCU\Software\kadr-test` (`KADR_TEST_REGISTRY`), справжнє налаштування windows не читають і не змінюють.
7. **права адміністратора.** якщо kadr запущено з підвищеними правами (наприклад, з адмін-термінала), він може зберігати в захищені папки. звичайний запуск — без підвищення (`asInvoker` у маніфесті).

## 8. дизайн інтерфейсу

процес: skills `impeccable` (контекст, напрям, контракт, фінальне рев'ю), `unslop` (правила ремесла: сітка 4 px, одна нейтральна гама, тихі рамки, текст), `design-taste-frontend` (з нього взято лише загальні принципи — він для маркетингових сайтів компаній, а не для вікна застосунку). продукт — PRODUCT.md, контракт напряму — `.impeccable/surfaces/settings-window.md`, ескізи раунду вибору — `.impeccable/mocks/decision/` (не в git).

**напрям «мітки обрізу»** (обрав користувач): кадр, який редагуєш, позначено чотирма кутами — тими самими, що в overlay і на іконці трею.

- **вікно налаштувань:** 520 px, системна тема, графітова нейтральна гама без акцентного кольору; групи hotkeys / after capture / saving / general на піднятих заокруглених поверхнях; рядок з фокусом — у мітках обрізу; гарячі клавіші — клавіші-«капи»; наступне ім'я файла — моноширинним шрифтом під полем; червоний — для конфліктів (тримаються, доки їх не виправлено) і для всіх помилок, що потребують уваги; підказки й інформаційні повідомлення червоним не бувають (рішення команди, 2026-11-11). змін не треба зберігати: вони застосовуються одразу.
- **overlay:** екран затемнено до ~55 %, виділення в повній яскравості з білою рамкою 1 px і білими мітками обрізу в кутах, підпис `801 × 501` над виділенням, підказка до першого натискання. без анімацій.
- **трей:** іконка-видошукач під тему панелі задач; стандартне меню win32 (у темній темі windows воно лишається світлим — документованого способу інакше немає).
- **мова:** англійська, lowercase.
