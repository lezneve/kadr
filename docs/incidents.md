# kadr / розбір інцидентів під час розробки

## 2026-11-11 — «відхилені» команди з емуляцією вводу виконались

### що сталося

агент (claude code) запустив дві команди powershell, які через `SendInput` натискали `ctrl+printscreen`, `alt+printscreen`, `ctrl+shift+printscreen` і `esc` для запущеного kadr. обидва рази інструмент повернув:

> the user doesn't want to proceed with this tool use. the tool use was rejected

і в розмові з'явилось «[request interrupted by user for tool use]». після першого разу користувач написав «я случайно», після другого — «почему interrupted?».

### що показують докази

траса kadr (`--trace`) записала обидва прогони повністю:

| час | подія |
|---|---|
| 15:34:17 | `hotkey screen` → знімок 2560×1600 збережено |
| 15:34:19 | `hotkey window` → знімок 2560×1528 збережено |
| 15:45:34 | `hotkey screen` → знімок збережено |
| 15:45:36 | `hotkey window` → знімок збережено |

інтервал 2 с між подіями відповідає `Start-Sleep 1.5` у скрипті. `ctrl+shift+printscreen` не дав події, бо в тодішній конфігурації він не був зареєстрований. отже, **обидві команди виконались до кінця** (принаймні до натискання `esc`).

агент спершу повідомив користувачу, що команду «відхилено і я зупиняюсь», не перевіривши стан. факт виконання знайшовся тільки пізніше, у трасі. знімки (зображення екрана користувача) лежали в тимчасовій папці й були видалені одразу після виявлення.

### причина

**встановлено:** команди почали виконуватись. повідомлення про відмову не означало, що процес не стартував.

**найімовірніше, але не підтверджено зсередини сесії:** користувач перервав виклик (esc), коли той уже виконувався. маркер «interrupted by user for tool use» з'являється саме при перериванні, і реакції користувача («случайно», «почему interrupted?») узгоджуються з випадковим натисканням. переривання зупиняє очікування результату, але не відкочує вже виконані дії: `SendInput` спрацьовує миттєво, файли вже записані.

**не встановлено:** чи показувався запит дозволу до запуску і як саме інструмент обробляє переривання запущеної команди (вбиває процес чи лише перестає чекати). це поведінка середовища claude code, не kadr; через `/feedback` відправлено опис для розробників середовища.

### що змінено

1. **правило для агента:** після будь-якої відмови або переривання команди з побічними ефектами — спершу перевірити фактичний стан (трасу, файли, процеси), і лише тоді повідомляти, що сталося.
2. **автоматичні тести не емулюють ввід.** `tests/smoke.ps1`, `tests/session.ps1`, `tests/soak.ps1` керують kadr повідомленнями у його власні вікна (`WM_HOTKEY`, `WM_TRAY`, повідомлення миші в overlay). реальні клавіатура й курсор не задіяні. ці повідомлення проходять ті самі гілки коду, крім доставки натискання системою.
3. **кожен тест працює в пісочниці:** окремий файл налаштувань, тимчасова папка, яка видаляється, `--test-private-clipboard` (копії не потрапляють в історію win+v), буфер обміну зберігається до тесту й відновлюється після.
4. **ввід, якого не можна змоделювати повідомленнями** (доставка натискання системою, реальний курсор, фокус) — тільки контрольований сценарій нижче.

### контрольований сценарій для тестів з реальним вводом

`tests/input.ps1`. агент **не запускає** його сам. запускає людина (або агент — тільки після окремого явного дозволу на конкретний прогін у чаті).

- перед стартом скрипт показує, що саме зробить, і чекає enter;
- зворотний відлік 5 с, протягом якого рух миші скасовує запуск;
- під час роботи будь-який рух миші не від скрипта перериває тест (перевірка позиції курсора між кроками);
- лише комбінації з модифікаторами; голий `printscreen` не натискається (snipping tool відкрив би свій інтерфейс і міг би зберегти знімок у папку користувача);
- пісочниця як у пункті 3; після тесту — звіт: що натиснуто, що kadr записав у трасу, які файли створено й видалено.

## 2026-11-11 — тестовий знімок потрапив у `C:\Windows\System32`

тест «помилка збереження» мав спиратися на заборону доступу до `C:\Windows\System32`. сесія працювала з правами адміністратора (як з'ясувалось пізніше, uac на машині вимкнено), тож kadr створив там папку й зберіг знімок екрана. файл і папку видалено одразу. тест переписано: тепер шлях проходить через звичайний файл, і створити його неможливо за будь-яких прав. висновок: тести не повинні покладатися на права доступу середовища.

## 2026-11-11 — на тестовій машині вимкнено uac

`EnableLUA = 0`: усі процеси облікового запису, включно з explorer, працюють з повним токеном адміністратора і високим рівнем цілісності. тому:
- усі ранні прогони kadr були з правами адміністратора, навіть «звичайні»;
- `runas /trustlevel:0x20000` і запуск через explorer теж дають повний токен;
- для перевірки «без прав адміністратора» тести створюють той токен, який uac видав би звичайному сеансу (`CreateRestrictedToken` з `LUA_TOKEN`, група administrators вимкнена, рівень medium) і запускають kadr через `CreateProcessAsUser`. система при цьому не змінюється.

побічний ефект саме цієї конфігурації: kadr зі стандартним токеном не може додати іконку в трей, бо explorer має вищий рівень цілісності (uipi). у звичайному сеансі з увімкненим uac explorer теж medium, і такої ситуації немає. kadr тепер повідомляє про відсутню іконку прямо (раніше — лише в трасі).
